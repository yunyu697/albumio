# S5 · 网格滚动流畅度（1 万项）

- 目的（`04-项目计划.md` §2）：确认虚拟滚动网格在 1 万项规模下能守住 60fps；若不能，先定降级方案再开 M2。
- 方法：`app/docs/spike/s5-scroll.html` 用与设计稿相同的参数（格宽 128、间距 12、内边距 12、文件名条 20）搭一个虚拟滚动网格，数据 1 万项，所有格子复用同一张已解码位图（把"解码 1 万张"从滚动测量里剔除）。连续滚动 600 帧，记录帧间隔与每帧 `render()` 的同步耗时。
- 运行器：`node scripts/spike-s5-scroll.mjs`（CDP 驱动无头 Edge；无头模式需 screencast 当帧泵，否则 rAF 不推进）。

## 实测

| 项 | 值 |
| --- | --- |
| 引擎 | Edge（Chromium）headless，`--disable-gpu`，DPR=1，视口 1200×700 |
| 列 / 行 | 8 列 / 1250 行 |
| 帧数 | 600 |
| 平均帧间隔 / FPS | 16.67 ms / 60.0 |
| p95 / p99 / 最大帧间隔 | 16.7 / 16.8 / 16.8 ms |
| >20ms 帧 / >33ms 帧 | 0 / 0 |
| `render()` 平均 / 最大 | 0.11 ms / 8.4 ms |
| `scrollWidth` / `clientWidth` | 1185 / 1185 |

## 结论

1. 虚拟化（只渲染可视行 ±2 行）+ 复用已解码位图，在 1 万项下滚动保持 60fps，单帧渲染成本远低于预算；**M2 不需要额外降级**。
2. `scrollWidth === clientWidth` 成立，网格不产生横向溢出。
3. 首帧 8.4 ms 是首次建行的成本，之后稳定在 0.1 ms 量级，说明"滚出新行才建 DOM"的窗口策略有效。

## 限制与后续

- **Linux WebKitGTK 未实测**：本机无 Linux 环境，无法运行 WebKitGTK。上表是 Windows WebView2 同源引擎（Chromium）的数据，只能证明"网格结构本身不超预算"，不能替代 Linux 结论。
- 已预置降级阶梯（若 M9 前的 Linux 复测不达标，按顺序启用）：
  1. 预取行数由 ±2 降为 ±1；
  2. 最小两档格宽改用 160px 的 L1 缓存（甚至 L0 直接上屏）代替 256px；
  3. 给网格单元加 `content-visibility: auto`；
  4. 缩略图并发解码数上限降到 2。
- 复测时点：M9 打包阶段在 Linux 实机/容器上复跑同一页与真实应用，把结论补进本文件。
