# S6 · `notify` 文件监听：事件序列、去抖、改名配对、溢出降级

- 目的（`04-项目计划.md` §2）：M8 的硬门槛。验证监听方案本身、去抖取值、改名配对、监听溢出时的降级路径。
- 环境：Windows 11 · NTFS（C:，本机 SSD）· Rust 1.77 · `notify 8.2.2`（8.x 最新稳定版，`rust-version = 1.77` 与项目一致）· 非递归监听单个目录。
- 复现（在 `app/src-tauri` 下，`notify` 只是 `albumio-core` 的 **dev-dependency**，不进运行时依赖）：

```
cargo run --release -p albumio-core --example watch_spike -- events   "$env:TEMP\albumio-s6"
cargo run --release -p albumio-core --example watch_spike -- burst    "$env:TEMP\albumio-s6" 1000
cargo run --release -p albumio-core --example watch_spike -- overflow "$env:TEMP\albumio-s6" 30000 0
```

- 代码：`app/src-tauri/crates/albumio-core/examples/watch_spike.rs`（每次运行重建自己的子目录；`%TEMP%\albumio-s6` 可随时删）。

## 1. 事件序列（单操作，逐条打印）

| 操作 | 实际事件（按到达顺序） | 结论 |
| --- | --- | --- |
| 新建文件 | `Create(Any)` + `Modify(Any)`（同一毫秒） | **一次新建 = 2 条事件**，必须按路径去重 |
| 追加写 4×4 KB | 1 条 `Modify(Any)` | 同一句柄的连续写会被合并；不能拿事件条数当写入次数 |
| 原路径 truncate 重写 | 2 条 `Modify(Any)` | 覆盖保存 = 纯 Modify，不会出现 Create/Remove |
| 原子替换：写 `.tmp` 再 rename 覆盖 | `Create(.tmp)` `Modify(.tmp)` **`Remove(目标)`** `Name(From .tmp)` `Name(To 目标)` | 覆盖式 rename 会先报旧目标 Remove，再报 From/To；批内最终状态必须按 stat 校正 |
| 改名（同目录） | `Name(From)` → `Name(To)`，相邻 | **没有 `RenameMode::Both`，也没有 cookie** |
| 连续 3 次改名 | `From1,To1,From2,To2,From3,To3` | 配对按到达顺序一一相邻，顺序稳定 |
| 移入子目录（子目录未被监听） | `Remove(b.jpg)` + `Modify(sub)` | 移出当前相册 = Remove；对目录路径的 Modify 应忽略 |
| 从子目录移回 | `Create(b.jpg)` | 移入当前相册 = Create，无法知道来源 |
| 删除 | `Remove(Any)` | 1 条 |
| 慢写 64×32 KB（跨 2.6 s） | `Create` + **1 条** `Modify`（在写完/关闭时到达） | Windows 按文件合并写入事件：不会因为分块写而产生几十条 |

要点：

1. **Windows 的 `EventKind` 只有 `Any`**，不区分文件/目录。判断类型必须靠 `stat` 或扩展名，不能靠 `CreateKind::File`。
2. **改名没有 cookie**：项目计划里写的「按 cookie 配对」是 Linux inotify 的概念；`notify` 的公开 API 不暴露 cookie。Windows 上实际是相邻的 `From` / `To` 两条事件，必须自己配对（见 §3）。
3. 事件延迟 0.3–4 ms（操作完成到回调），本地盘可忽略。

## 2. 突发：去抖取值

| 场景 | 操作耗时 | 事件数 | 首→末跨度 | 突发内最大事件间隔 |
| --- | --- | --- | --- | --- |
| 4 线程新建 1000 个文件 | 449–572 ms | 2000（1000 Create + 1000 Modify） | 446–569 ms | **10.6 ms** |
| 4 线程删除 1000 个文件 | 410 ms | 1000（全 Remove） | 408 ms | **4.8 ms** |
| 16 线程复制 30000 个文件 | 15.2 s | 90002（30001 Create + 60001 Modify） | 16.7 s | 复制中 ≤ 数 ms；末尾 1502 ms 是脚本等待 |

- 本地 SSD 的突发内部间隔是**个位数毫秒**，500 ms 的静止窗口有 50 倍余量；换成网络盘 / HDD，间隔会拉长到几十到几百毫秒。
- **建议：静止窗口 300 ms，硬上限 1200 ms**。理由：
  - 300 ms 对本地是 28 倍余量，对网络盘（每次文件复制间隔 50–200 ms）也能合并成一个批次；
  - 计划里的 500 ms 不是错，只是比实测需要多 200 ms 的可见延迟（外部改名后网格最多晚 0.5 s 才变）；
  - 1200 ms 硬上限用于「持续不断的复制」：从第一条事件起最多等 1.2 s 就处理一批，避免用户看着界面一直不动。
- 批次内**按路径去重、后写覆盖先写**：1000 个文件 2000 条事件，去重后是 1000 个路径；实际落库/刷 UI 只处理这 1000 个。
- 去抖只解决「事件太多」，**不保证文件写完了**：跨平台时仍要在处理批次前 `stat` 一次（大小/mtime 与上次相同才解码），否则网络盘中转 >300 ms 的复制会拿到半截文件。

## 3. 改名配对

`notify` 8 在 Windows 上给出的是相邻的 `Modify(Name(From))` 与 `Modify(Name(To))`，`RenameMode` 永远是 `From`/`To`，`Both` 计数为 0。配对规则：

1. 在同一去抖批次内按到达顺序扫描，维护 `pending_from`：
   - `From` → 暂存；
   - `To` 且 `pending_from` 存在 → 配成一次改名 `(from, to)`，清空；
   - `To` 但没有 `pending_from` → 按 Create 处理（文件从其它目录移入）；
   - 批次结束时仍有 `pending_from` → 按 Remove 处理（文件移出当前目录）。
2. 若某平台给出 `RenameMode::Both`（macOS 可能出现），`paths[0]`/`paths[1]` 直接当 `(from, to)`，跳过上面的状态机。
3. **配对后仍要按最终状态校正**：同一批次里可能先出现 `Remove(a.jpg)` 再出现 `rename(.tmp → a.jpg)`（原子替换）。对批次里的每个路径做一次 `stat`：存在就 upsert，不存在就删除。改名配对只用于**迁移数据库行**（保住评分、标签、编辑记录），不用来直接决定 UI 增删。
4. 移出当前目录在 Windows 上不是一个改名事件，而是 `Remove + Modify(目录)`；所以「监听只看当前目录、不递归」是够的，但目录路径的 Modify 必须忽略。
5. 文件名过滤：`.tmp` / `.crdownload` / `~$*` / `Thumbs.db` / `desktop.ini` 及非图片扩展名在入批前就丢弃；`stat` 是目录的也丢弃（Windows 的 kind 不区分，只能靠 stat）。

## 4. 溢出与降级

实测（本机 SSD）：

| 场景 | 结果 |
| --- | --- |
| 消费者线程阻塞 3 s，同时复制 6000 个文件 | 18002 条事件**一条不少**，0 错误；解阻塞后全部到达；溢出后新建文件的事件正常到达 |
| 16 线程复制 30000 个文件 | 90002 条事件，0 错误、0 丢失（每个文件 3 条：Create + 2 Modify） |

原因：`notify` 内部有独立读取线程，把我们阻塞的消费者和操作系统缓冲区隔开了（我们用的是无界 channel）。**在本地盘上，30k 文件 / 90k 事件的突发也没能把 Windows 的 `ReadDirectoryChangesW` 缓冲打满**。真正的风险从「丢事件」变成了「积压占内存」：一条事件约 150–250 B，1.8 万条积压约 3–5 MB，量级可接受，但不能无限涨。

跨平台差异（按 `notify` 文档，未在本机实测）：

- macOS FSEvents：`must scan subdirs` 会以 `Flag::Rescan` 出现在事件属性里；
- Linux inotify：内核队列溢出会以 `Err` 返回（`IN_Q_OVERFLOW`）；
- Windows：缓冲溢出时 `ReadDirectoryChangesW` 返回 `ERROR_NOTIFY_ENUM_DIR`，`notify` 以 `Err` 报出。

降级协议（M8 直接按这个实现）：

1. 收到 `Err` 或带 `Rescan` 标志的事件 → 立刻把当前监听标记为「不可信」，**停止应用增量**，对当前目录做一次整目录重建（readdir + stat）。
2. 重建成本实测：6001 个文件 4.0 ms、30001 个文件 12.5 ms（热缓存）。这个量级不需要进度条，直接做完再刷网格。
3. 给一条非模态提示：「目录变化可能未全部捕获，已自动刷新」+ 保留 `F5` 手动刷新；不弹模态、不阻断浏览。
4. 60 秒内连续 3 次 `Err` → 降级为 2 s 轮询（只比目录 mtime + 可见区 stat），并提示用户；恢复条件为下一次手动刷新成功。
5. 积压保护：消费者每批最多处理 2000 条事件；剩余积压 > 50000 条时直接丢弃队列并走第 1 步整目录重建（用一次 12 ms 的重建换掉几十 MB 内存）。
6. 周期校验（R9 的兜底）：窗口重新获得焦点时、以及空闲时每 30 s，比较目录 mtime；目录 mtime 只在直属子项增删/改名时变化，**文件内容原地修改不会触发**，所以这条只兜「漏了增删」，内容修改仍靠事件通道与手动刷新。

## 5. 结论（M8 可以直接开工）

| 项 | 结论 |
| --- | --- |
| 方案 | `notify 8` + `RecommendedWatcher`，对当前目录 `RecursiveMode::NonRecursive`；事件消费放独立线程，UI 只收批次 |
| 去抖 | 静止窗口 **300 ms**，硬上限 **1200 ms**；批内按路径去重，后写覆盖先写 |
| 改名 | 按到达顺序配对相邻 `From`/`To`（无 cookie）；兼容 `Both`；配对只用于迁移 DB 行，增删以 `stat` 结果为准 |
| 溢出 | `Err` / `Rescan` → 停止增量 → 整目录重建（30k 文件 12.5 ms）→ 提示 + `F5`；60 s 内 3 次 → 2 s 轮询 |
| 风险 | 本地盘上未能复现事件丢失；最大风险变为「消费者卡住导致内存积压」，已用批上限 + 积压阈值兜住 |
| 与计划差异 | 计划写 500 ms 去抖：实测支持 300 ms，500 ms 也不错，只是多 200 ms 延迟；「按 cookie 配对」需要改写成「按 From/To 顺序配对」，因为 `notify` 不暴露 cookie |

## 6. 限制

- 只测了 Windows + NTFS + 本地 SSD；HDD、SMB/网络盘、macOS、Linux 未实测（本机无对应环境），上表跨平台部分依据 `notify` 文档。
- `notify` 8.2.2 的行为不等于 9.x（当前 9.0 还是 rc），M8 锁 8.x。
- 慢写测试表明「一次写入一文件只报一条 Modify」，这是 Windows 的合并行为；其它平台分块写可能报多条，所以去抖按路径合并是跨平台必需项，不是优化项。
