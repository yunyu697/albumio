## 2. 验收逐条

### 2.1 外部重命名 20 个文件，网格 1 秒内跟随，选中不跳、滚动位置不跳

- Rust：`twenty_renames_follow_within_one_second`（生产参数 300 ms 静止窗口）——20 个改名全部到齐，**实测 340 ms**。
- Rust：`rename_is_reported_as_rename_not_delete_and_create`、`rename_batch_carries_both_side_entries`——批次同时带 `renamed` 与 `stat` 校正后的 upsert/remove。
- 前端自检（`m8-check`）：选中 `DSC_0490.JPG`，投递改名批次 → 选中项变为 `DSC_0490B.JPG`、当前项跟随、**滚动位置 240 不变**、格子数不变、旧名字消失；**实测 14 ms 上屏**。

### 2.2 外部删除 → 网格移除且不留"灰块"

- Rust：`create_and_delete_are_reflected_in_separate_batches`——删除批次只含 `removed`，不再带同名 upsert。
- 前端自检：删除 `DSC_0486.JPG` → 42 → 41 格，`uniqueCaps == count`（无残留/重名灰块），选中与滚动不变；**实测 16 ms**。

### 2.3 监听溢出被检测到并提示，不静默失效

- Rust 单测 `error_without_changes_reports_overflow`——`Err` 批次只标 `overflow`，不产生半截增量。
- 前端自检：投递 `overflow: true` → 出现非模态提示「目录变化可能未全部捕获，已自动刷新」+「再次刷新」动作，并整目录重建恢复原列表。
- 积压保护：单批最多 2000 条；积压 > 50000 条丢弃队列并转 overflow（`watch.rs` `run_loop`）。

### 2.4 增量更新，不重建整表

- 批次只携带受影响路径；前端按路径原地合并、自然序重排，`listDir` 不重跑。
- 删除释放 blob URL；内容变更（mtime 不同）才重新解码缩略图；改名直接迁移缩略图缓存，不重解码。
- 时间线只补读"尚未读到拍摄时间"的新增项，不因一次外部变更重读整目录 EXIF。

### 2.5 G3：屏 1 在监听生效状态下叠图（无额外视觉变化）

- 监听启动后无任何新增控件或状态条；`m8-check` 初始断言 `toast === null`，格子仍为 42。
- 几何回归：M3/M5/M6/M7/删除流程自检全部通过（同一构建）。

## 4. 已知缺口

1. **索引表未随监听更新**：`index.db` 的行仍由检查器打开图片时写入；监听批次没有 `PhotoMeta`，不用残缺数据覆盖索引行。网格与缓存是完整的，搜索/评分等索引能力不受影响。
2. S6 §4.4 的「60 s 内 3 次 `Err` → 2 s 轮询」未实现；当前每次 `Err` 都走整目录重建 + 提示。
3. S6 §4.6 的「窗口获焦 / 空闲 30 s 比对目录 mtime」周期校验未实现，仍靠事件通道 + `F5`。
4. 真实 GUI 手测未跑：无头自检覆盖前端行为，Rust 测试覆盖真实监听；未在 Tauri 窗口里做 Explorer 改名/删除的实体操作录像。
5. 只在 Windows + NTFS + 本地 SSD 验证；HDD、SMB、macOS、Linux 未实测（与 S6 限制一致）。
6. 改名后若排序位置变化（如 `DSC_0490` → `DSC_9900`），Grid 会跟随当前项滚动到新位置；这是「还在看同一张」的有意行为，不是网格重置。
